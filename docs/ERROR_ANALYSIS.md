## 2. 오답 귀착 — 기존 분류표는 병목을 잘못 지목하고 있었다

`eval/score.py` 의 분류는 후보 목록만 보므로 `no_candidate`(135장, 20.3%)를
"검출 / 박스 필터 재현율"로 지시한다. 실제로는 GT 박스와 대조해야 갈린다.
실패 195건 전부에 대해 **정답 exp 박스를 검출 결과와 IoU≥0.3으로 매칭**하고,
그 크롭을 강제로 인식시켜 원인을 하나로 귀착시켰다 (`results/kist_run/attribution.json`).

| 원인 | 장수 | 비중 | 뜻 |
|---|---|---|---|
| `rank_miss` | 63 | 32.3% | 검출은 됐으나 순위가 `max_k=9` 밖 |
| `det_miss` | 54 | 27.7% | 검출기가 박스 자체를 못 냄 |
| `recog_miss` | 54 | 27.7% | 상위에 있고 읽었으나 글자가 틀림 |
| `parse_miss` | 15 | 7.7% | 정확히 읽었으나 정규식이 못 잡음 |
| `earlystop_miss` | 8 | 4.1% | 정답 크롭을 읽기 전에 조기 종료 |
| `select_miss` | **1** | 0.5% | 정답이 후보에 있었는데 다른 걸 고름 |

**선별(select)은 사실상 해결돼 있다 — 195건 중 1건.** README가 "이 과제의 본질은
선별"이라고 쓴 부분은 이 평가셋에서는 더 이상 맞지 않는다. 병목은 **순위(63)와
검출(54)** 로 옮겨갔다.

### 2-1. `det_miss` 54건은 전부 검출기다

박스 필터가 버린 것은 **0건**이다. 54건 모두 `Engine.detect()` 가 박스 자체를
내지 못했다. 놓친 GT 박스의 기하 특성은 높이 p50 27.8px · 종횡비 p50 5.9 로
**지극히 평범하다** — 작아서 놓친 게 아니다. 필터 튜닝으로는 회수할 수 없고,
`det_side` 상향(Config 주석의 실측: 640px 83.6% → 960px 86.8%) 또는
날짜 전용 검출기(Track B, `docs/DETECTOR_PLAN.md`)가 필요한 구간이다.

### 2-2. `rank_miss` 63건의 정답 박스 순위

```
9,9,9,9,9,9,9,9,10×7,11×10,12×5,13×4,14×6,15,16×9,17,18×3,20×2,22,23×2,27×2,28,32
p50 13 · max 32   (필터 통과 박스 수 p50 34)
```

`max_k=9` 를 20으로 올리면 54건이 사정권에 들어온다. 그리고 그 크롭을 읽었을 때
**현재 파서로도 52건이 정답 날짜를 파싱**한다 — 즉 이 63건은 순수하게 "덜 읽어서"
놓친 것이다.

가설이 아니라 665장 전체를 다시 돌려 측정했다.

| | max_k=9 (현행) | max_k=20 |
|---|---|---|
| 점수 | 36.85 / 50 | **40.21 / 50** |
| 완전일치 | 70.7% | **77.6%** |
| 속도 | 365 ms/img | 484 ms/img |
| 총 소요 | 243초 | 322초 (예산 2400초의 13%) |

**+3.36점 (+9.1%p 완전일치)** 을 장당 119ms에 산다. `no_candidate` 는 135→79장으로

주의: `wrong_candidate` 가 4→8장, `misread` 가 46→51장으로 **늘었다.** 깊이 읽을수록
오답 후보도 함께 들어오므로, `max_k` 상향은 선별 규칙에 더 큰 부담을 준다.
그래도 순증이 압도적이다.

## 4. 확인된 버그: 구분자 주변 공백이 날짜를 통째로 죽인다

```
'2022.09.27'   → 2022-09-27  ✅
'2022. 09. 27' → 후보 없음    ❌
'2020. 11.18'  → 후보 없음    ❌
'2021 .06.09'  → 후보 없음    ❌
```

원인은 `itda_ocr/parse.py` 의 `_SEP = r"[.\-/ ]"` 와 역참조 `\2` 다. 역참조가
**양쪽 구분자의 완전 일치를 강제**하는데, `2022. 09. 27` 은 한쪽이 `.`, 다른 쪽이
`. `(점+공백)이라 매치가 깨진다.

수정 방향은 `\s*` 를 **캡처 그룹 바깥**에 두는 것이다:

```python
rf"(20\d{{2}})\s*({_SEP})\s*(\d{{1,2}})\s*\2\s*(\d{{1,2}})"
```

텍스트를 치환하지 않으므로 `normalize()` 의 **길이 보존 불변식이 유지**된다
(`_embedded` 의 품목보고번호 판정이 원문 인덱스에 의존하므로 이 성질이 필수다).

효과: 파이프라인이 이미 읽은 텍스트만으로 **11장**이 회수된다 (상한 +0.76점).
`max_k` 상향과는 거의 독립이다 — rank_miss 63건은 공백 보정 유무와 무관하게
52↔53건으로 사실상 같다.

## 5. 기각한 가설: "제조일자 선별 규칙"

완전한 날짜를 냈지만 틀린 25장 중 **20장이 GT보다 과거**이고, 그중 11장이
정확히 약 1년(Δ=364·365) 또는 약 18개월(Δ=547·549) 전이다. Δ=364가 6장인데,
이는 "제조일 + 1년, 전일까지"라는 국내 표기의 전형이다.

```
test_00256  GT 2021-12-27  예측 2020-12-28  Δ364일
test_00447  GT 2022-03-05  예측 2021-03-06  Δ364일
test_00461  GT 2021-12-02  예측 2020-12-03  Δ364일
test_00525  GT 2021-04-20  예측 2020-04-21  Δ364일
test_00542  GT 2021-10-21  예측 2020-10-22  Δ364일
test_00625  GT 2022-01-31  예측 2021-02-01  Δ364일
```

여기까지만 보면 "두 후보의 날짜 차가 약 1년이면 나중 것을 고른다"는 규칙이
자명해 보인다. **그러나 후보 목록을 확인하면 12장 중 11장은 후보가 하나뿐이다** —
소비기한 크롭은 아예 읽히지도 않았고, 제조일자만 후보로 올라와 있다.

```
test_00256  parse_miss      후보: ['2020-12-28']            정답 포함=False
test_00461  earlystop_miss  후보: ['2020-12-03']            정답 포함=False
test_00525  recog_miss      후보: ['2020-04-21','2021-04-20'] 정답 포함=True  ← 유일
```

즉 이것은 **선별 실패가 아니라 상류(순위·인식·조기종료) 실패의 증상**이다.
선별 규칙을 추가해도 12장 중 1장만 고쳐진다. §2의 귀착 결과(`select_miss` 1건)와
정확히 일치한다.

## 9. 퇴행 88장의 원인 — NanoDet 박스가 글자에 너무 붙는다

퇴행 88장의 모양:

| | 장수 |
|---|---|
| **일자만 틀림** (연·월은 정답) | **37** |
| 답이 NONE 으로 사라짐 | 25 |
| 연도만 틀림 | 8 |
| GT 가 NONE 인데 날짜를 냄 | 9 |
| 그 외 | 9 |

일자 한 자리가 틀리는 형태가 지배적이다. 원인은 **크롭 경계**다.

- `Engine.crop()` 은 박스를 **그대로** 잘라낸다 (여백 없음).
- RapidOCR DB 검출기는 `unclip_ratio=1.6` 으로 **이미 부풀려진** 박스를 준다.
- NanoDet 회귀 박스는 글자에 딱 맞게 나온다 → 첫/마지막 글자가 잘려 나간다.

같은 이미지에서 박스만 각 변으로 넓혀 다시 인식한 결과
(`--nanodet-expand` 를 0 / 0.08 / 0.15 로 바꿔 상위 3개 크롭을 인식시킨 것):

```
test_00157  GT 2021-08-04   pad 0%  '2021.08.0'    →  pad 8%  '2021.08.04'
test_00205  GT 2021-06-25   pad 0%  '5.06.2021'    →  pad 8%  '25.06.2021'
test_00194  GT 2025-08-14   pad 0%  '2025.08.1'    →  pad 15% '2025.08.14'
test_00121  GT 2022-03-31   pad 0%  '31-0'         →  pad 8%  '31-03'
test_00109  GT 2020-10-21   pad 0%  '2020.10.'     →  pad 15% '2020.10.21'
test_00153  GT 2023-04-30   pad 0%  '-04-2023'     →  pad 15% '0-04-2023'
test_00116  GT 2021-12-01   pad 0%  '2021.12.0'    →  pad 8%  '2021.12.01'
```

오독 101건 중 **25건**은 인식 텍스트에 정답 숫자열의 앞/뒤 한 글자 결손이
그대로 남아 있다. 위 §8-1 의 "선별 실패 25건"도 상당수가 같은 뿌리다 —
같은 스탬프를 겹치는 박스 여러 개로 읽어 `2020-10-21` / `2020-10-29` / `2020-10-20`
가 동시에 후보로 올라오고, `rank()` 의 동점 처리(나중 날짜 우선)가 잘린 쪽을 고른다.

## 10. 적용한 수정 — `nanodet_expand = 0.10`

`NanoDetDetector` 가 반환 박스를 각 변으로 넓히도록 했다. 상수는 검출기가 소유한다
(`itda_ocr/nanodet_det.py: DEFAULT_EXPAND`) — 깨진 계약이 거기서 났기 때문이다.
`Engine` · `Config` · `predict.ipynb` 가 모두 이 값을 참조한다.

### 10-1. 스윕 — 8% 가 최적인가?

665장 전체를 10개 값으로 다시 돌렸다 (`results/sweep/`, `results_pad_sweep.log`).

| expand | 점수 | 완전일치 | | expand | 점수 | 완전일치 |
|---|---|---|---|---|---|---|
| 0.00 | 39.71 | 75.6% | | 0.10 | **41.41** | **79.7%** |
| 0.02 | 40.50 | 77.7% | | 0.12 | 41.33 | 79.7% |
| 0.04 | 39.94 | 76.1% | | 0.15 | 41.13 | 78.9% |
| 0.06 | 40.83 | 78.3% | | 0.20 | 40.92 | 78.0% |
| 0.08 | 41.15 | 79.2% | | 0.30 | 41.07 | 79.2% |

**최고점은 0.10 이지만 그걸 근거로 고르면 안 된다.** 견고성 점검 결과:

- 부트스트랩 95% CI (장당 점수 차, 2000회 재표본):
  - `0.00 → 0.10` **+1.71 [+0.42, +2.98]** — 0을 포함하지 않는다. **수정 자체는 실재한다.**
  - `0.08 → 0.10` +0.26 [−0.42, +0.92] — 0을 포함한다.
  - `0.10 → 0.12` −0.08 [−0.80, +0.58] · `0.10 → 0.15` −0.29 [−1.22, +0.60] — 마찬가지.
- 평가셋을 홀수/짝수 절반으로 나눠 각각 최적값을 고르면 **홀수 0.30, 짝수 0.08** 로 갈린다.
- 0.06~0.15 구간 점수 평균 **41.17 ± 0.23**.

즉 0.06~0.15 는 서로 구분되지 않는 **평탄 구간**이고, 소수점 둘째 자리를 고르는 것은
665장에 대한 과적합이다. 그래서 최고점이 아니라 **평탄 구간의 중앙 0.10** 을 골랐다.
기전과도 맞는다 — 날짜 문자열이 10자 안팎이므로 10% ≈ **글자 한 칸**의 여백이다.

곡선이 매끈하지 않은 것(0.04 에서 39.94 로 꺼짐)도 같은 이야기다. 장마다 "끝 글자가
크롭 안에 들어오는" 임계 여백이 달라서, 값을 조금 바꾸면 수십 장이 양방향으로 뒤집힌다
(`0.08 → 0.10` 에서 개선 25장 / 퇴행 17장).

## 11. 기각한 개선: `max_k` 9 → 20

**결론: 채택하지 않는다.** 순위 수정(§12) 이후 43.47 → 43.28 (−0.19) 로
오히려 해가 된다. 아래는 그 경위다.

### 11-1. 박스가 5개뿐이라 무의미한가 — 절반만 맞다

"NanoDet 은 박스를 5개만 내는데 max_k 를 올려봐야 의미 없지 않나" 는 절반만 맞다.
필터 통과 박스 수는 p50 5 지만 꼬리가 두껍다 —
p75 8 · p90 12 · p99 19 · max 20, **9개를 넘는 이미지가 111장(16.7%)** 이다.
(그리고 `filter_boxes` 는 NanoDet 출력에서 한 개도 버리지 않는다. 원본과 통과
분포가 모든 백분위에서 같다 — 날짜 전용 검출기가 이미 날짜 모양만 내기 때문이다.)

`max_k` 9 → 20 으로 **점수가 바뀐 이미지는 14장(개선 11 / 퇴행 3)이고 그 14장이
전부 "박스 > 9" 집단**이다. 박스 ≤ 9 인 554장은 소수점까지 동일하다. 인과가 깨끗하다.

| 집단 | 장수 | max_k=9 | max_k=20 |
|---|---|---|---|
| 박스 > 9 | 111 | 33.60 / 50 | **35.90 / 50** |
| 박스 ≤ 9 | 554 | 42.98 / 50 | 42.98 / 50 |

박스가 많은 이미지가 원래 훨씬 어렵다(33.60 vs 42.98) — 박스가 많다는 건 날짜 모양
후보가 여럿이라는 뜻이기 때문이다.

**expand 와 성격이 다르다.** 박스가 20개를 넘는 이미지는 **0장**이므로
(`NanoDetDetector.max_det = 20` 이 상한), `max_k=20` 은 "20을 골랐다"가 아니라
**"검출된 걸 전부 읽는다"** 이다.

⚠️ **여기까지가 §12 를 발견하기 전의 결론이다.** 이 +0.38 은 개선이 아니라
**망가진 순위에 대한 보상**이었다 — 정답 박스가 5~9위로 밀려나 있으니 더 깊이
읽을수록 주워 담을 게 있었던 것이다. 순위를 고치자 부호가 뒤집힌다(§12-2).

## 12. `filter_boxes` 가 검출기의 순위를 버리고 있었다 (+2.06)

§10 과 **같은 종류의 결함**이 하나 더 있었다. 검출기를 갈아끼우면서 그 뒤 단계가
전제하던 계약이 조용히 깨진 경우다.

### 12-1. 증상과 원인

`filter_boxes` 는 통과한 박스를 `-_date_prior(w, h, ratio)` 로 **재정렬**한다.
종횡비가 실측 중앙값 5.4 에 가까울수록 위로 올린다. 이는 **범용 텍스트 검출기용
설계**다 — RapidOCR DB 박스에는 "날짜다움" 점수가 없으니 기하로 추측할 수밖에 없다.

NanoDet 은 단일 클래스 `date` 검출기라 **박스 점수가 곧 날짜다움**이고
`detect()` 가 점수 내림차순으로 준다(순위 1 점수 중앙값 0.843, 순위 2 는 0.180).
그 위에 종횡비 재정렬을 덮으면 그 신호가 통째로 버려진다.

소비기한 박스 recall@K (665장, IoU ≥ 0.3):

| K | NanoDet 점수 순서 | `filter_boxes` 재정렬 후 | 차이 |
|---|---|---|---|
| 1 | **84.7%** | 50.2% | **−34.4%p** |
| 2 | 94.7% | 70.1% | −24.7%p |
| 3 | 95.9% | 81.8% | −14.1%p |
| 5 | 96.8% | 91.0% | −5.9%p |
| 9 | 97.3% | 96.1% | −1.2%p |
| 20 | 97.6% | 97.6% | 0.0%p |

`nanodet_det.py` 독스트링은 이 점수가 "filter_boxes 뒤 순위에도 반영된다"고 적고
있었으나 **사실이 아니었다.** 그 한 문장이 결함을 가리고 있었다.

### 12-2. 수정과 결과

순위 정책을 `Engine.detect_and_filter()` 한 곳으로 모으고, NanoDet 경로에서는
**거르기만 하고 다시 줄 세우지 않는다**(`filter_boxes(..., rerank=False)`).
호출부 4곳이 모두 이 메서드를 쓴다 — 조건문을 호출부마다 두면 이번 같은 누락이 또 난다.

| 지표 | 재정렬(기존) | **점수 순서 보존** |
|---|---|---|
| 정확도 점수 | 41.41 | **43.47 / 50 (86.9%)** |
| 완전일치 | 530장 (79.7%) | **563장 (84.7%)** |
| year / month | 88.6% / 91.4% | **91.0% / 93.7%** |
| day / final_date | 84.1% / 80.6% | **87.8% / 85.3%** |
| `misread` | 63 | **40** |
| `no_candidate` | 33 | 27 |
| 장당 p50 | 291 ms | 196 ms |

**Δ +2.05, 95% CI [+1.17, +2.98]** (개선 48장 / 퇴행 11장) — 0을 넉넉히 제외한다.
정답이 1~2위로 올라오니 첫 배치(`top_k=3`)에서 끝나는 이미지가 늘어 **속도도 붙는다.**

그리고 §11-1 의 `max_k` 이야기가 뒤집힌다:

| | max_k=9 | max_k=20 |
|---|---|---|
| 순위 수정 **전** | 41.41 | 41.80 (+0.38) |
| 순위 수정 **후** | **43.47** | 43.28 (**−0.19**) |

순위가 망가져 있을 때는 "더 깊이 읽기"가 보상이 됐지만, 순위를 고치고 나면 깊이
읽을수록 미끼 후보(`wrong_candidate` 28 → 31)만 들어온다. **증상을 보상하는 손잡이는
근본 원인을 고치면 부호가 뒤집힌다** — `max_k` 는 9로 둔다.
